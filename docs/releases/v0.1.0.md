# kasane-pdf v0.1.0

## Overview

kasane-pdf is an independent PDF engine written in Rust: a strict
parser, a page renderer, positioned text extraction, a document
rewriter and an incremental editor, with no dependency on PDFium,
MuPDF or Poppler. This is the first public release. The crate is
`kasane-pdf` on crates.io, licensed under the Apache License 2.0.

## Highlights

- **Strict by default, recovery by choice.** `Document::from_bytes`
  follows ISO 32000-1 and refuses malformed input with a typed error;
  `Document::from_bytes_recovering` rebuilds damaged files and reports
  every assumption it made.
- **Everything is bounded.** Every unbounded operation — input size,
  reference depth, decoded bytes per operation, operator counts, pixel
  buffers, mesh subdivision, edit budgets — is capped by a `Limits`
  field. Hostile input never panics or runs unbounded.
- **No partial results.** A construct the engine cannot process
  exactly is a typed `Error::Unsupported` / `Error::Structure`, never
  a silent skip; unavoidable approximations (colour profiles,
  substituted fonts) are reported on the result.
- **Incremental save with a signature-safe policy.** Edits can be
  appended as a new revision that keeps the original bytes verbatim;
  edits a signer did not permit are refused. Signatures are detected,
  never verified cryptographically, and never reported as valid.
- **Measured compatibility.** A 511-file corpus of public test suites
  and real-world documents is rendered, extracted and rewritten on
  every page and cross-checked against Poppler and qpdf in CI.

## Getting Started

```toml
[dependencies]
kasane-pdf = "0.1"
```

```rust
use kasane_pdf::{pixmap_to_png, render_page, Document, RenderOptions};

let data = std::fs::read("input.pdf")?;
let doc = Document::from_bytes(&data)?;
let page = render_page(&doc, &doc.pages()[0], &RenderOptions::default())?;
std::fs::write("page-1.png", pixmap_to_png(&page.pixmap)?)?;
```

Rust 1.92 or newer. The `kasane-pdf` CLI (`cargo install kasane-pdf`)
exposes rendering, text extraction, inspection, rewriting and the
editing commands. See the README and `docs/getting-started.md`.

## Supported Features

- **Parsing:** object layer, classic and stream cross-reference
  sections, `/Prev` chains, hybrid files, object streams, all standard
  stream filters (Flate, LZW, ASCII85, ASCIIHex, RunLength with
  predictors; DCT, JBIG2, CCITT, JPX for images), page tree with
  inherited attributes, named destinations.
- **Rendering:** paths and clipping, every colour-space family of
  §8.6, ExtGState with soft masks and all blend modes, transparency
  groups, images with masks, inline images, shadings of all seven
  types, tiling and shading patterns, text in TrueType, Type 1, CFF,
  OpenType, Type 0 (CID) and Type 3 fonts with rendering modes 0–7,
  vertical writing, optional content, annotation appearances and
  synthesised form-field / markup appearances, `/UserUnit`.
  Non-embedded Standard 14-style fonts use bundled Liberation
  substitutes (reported, never silent).
- **Text extraction:** one positioned character per code with Unicode
  through `/ToUnicode`, the encoding or `/ActualText`.
- **Writing and editing:** full rewrite; an `Edit` session for
  `/Square` annotations, annotation modification and removal,
  form-field values and `/Info`, written as a rewrite or an
  incremental update.
- **Inspection:** structural dumps, read-only redaction diagnosis and
  residual-information audit; experimental scoped content editors.
- **Feature `cjk-fallback`:** Adobe-Japan1 predefined CMaps, CID →
  Unicode table and Noto Sans JP for non-embedded Japanese CID fonts
  (assets ship in the crate).

## Known Limitations

- No document creation from scratch; editing starts from an existing
  file.
- Encrypted documents are refused.
- Signatures are detected, not verified; a full rewrite of a signed
  document is always refused.
- Knockout transparency groups, shading-pattern `/ExtGState`,
  non-embedded Symbol / ZapfDingbats and non-Japan1 CJK fonts, Type 3
  fonts in clipping modes are refused.
- No colour management beyond exact matrix/TRC ICC profiles, no
  hinting or shaping, no layout analysis in text extraction.
- `Document` is single-threaded.
- The experimental `remove_*` editors are content editors, not
  redaction.

The complete list is in `docs/limitations.md`.

## Compatibility

On the 427 well-formed files of the compatibility corpus: strict
parse 404, render (every page) 370, text 390, rewrite 355, all four
315. Of 413 rewritten files, every one reparses with an identical
object graph; 1,442 pages compared identically with Poppler; no
rewrite introduced a qpdf or Poppler diagnostic; 43 adversarial files
are refused without crash or timeout. These numbers describe that
corpus, not a general claim — see `docs/compat-corpus.md`.

## Security

Untrusted input is the design assumption: resource limits on every
operation, typed refusals, no `unsafe` outside four documented
lifetime transmutes in the font loader, no network or filesystem
access from the library. Report vulnerabilities privately through
GitHub's security advisories (see `SECURITY.md`).
