# kasane-pdf v0.5.1 — rendering robustness (R2, R4)

The two robustness items deferred from 0.5.0 (`plans/v0.5.0.md` §24):
R2, a `max_xobject_depth` default derived from a stack measurement, and
R4, structured render fuzzing with a nightly job. R1, R3 and the
recovery rules (phase E) stay planned for 0.6.

## 1. Where the renderer recurses

Every path that runs a content stream inside another one re-enters the
interpreter (`run` → `execute`):

| path | entered through | bounded by |
|---|---|---|
| Form XObject (`Do`) | `do_form` | `max_xobject_depth` |
| transparency group (a form's `/Group`) | `do_form` → `run_in_layer` | `max_xobject_depth`; layer memory by `max_render_buffer_bytes` |
| soft mask (`gs` with `/SMask`, its `/G`) | `render_soft_mask` → `do_form` | `max_xobject_depth` |
| annotation appearance | `draw_annotations` → `do_form` | `max_xobject_depth` |
| Type 3 glyph procedure | `show_type3_glyph` | `max_xobject_depth` |
| tiling pattern cell | `paint_tiling` → `paint_tiles_*` | a separate fixed depth of 8 (`MAX_PATTERN_DEPTH`) |

Form and pattern levels can interleave, so the stack holds up to
`max_xobject_depth` + 8 levels. Cycles are refused by the form and
pattern stacks (`CycleDetected`) long before either bound. The editors'
walker (`diagnose_redaction`, `remove_region`) has its own recursion over
forms under the same limit; `remove_text` refuses nested forms.

## 2. R2 — the stack per nesting level

Measured with a probe that renders a chain of N levels of one path in a
thread of a given stack size, in a child process (an overflow kills the
probe, never the measurement), binary-searching the smallest stack that
works; macOS arm64, rustc nightly 2026-10-28 / stable.

**Before** (v0.5.0 code), minimal stack at depth 32 / 48 / 64:

| path | debug | release |
|---|---|---|
| form | 819 / 1203 / 1587 KiB | 115 / 179 / 227 KiB |
| group | 899 / 1315 / 1715 | 115 / 179 / 227 |
| soft mask | 1315 / 1955 / 2579 | 179 / 275 / 355 |
| Type 3 | 1043 / 1539 / 2019 | 131 / 195 / 243 |
| annotation | 819 / 1187 / 1571 | 115 / 179 / 227 |

The operator dispatch (`execute`, one large `match`) kept its whole frame
on the stack at every level. **Change:** the operators that re-enter the
interpreter (`Do`, `gs`, text showing, path painting) are dispatched
from a small frame before the match. No behaviour change.

**After**, same probes:

| path | debug | release |
|---|---|---|
| form | 323 / 467 / 595 KiB | 83 / 131 / 179 KiB |
| group | 403 / 563 / 739 | 99 / 131 / 179 |
| soft mask | 819 / **1203** / 1603 | 163 / **227** / 307 |
| Type 3 | 579 / 819 / 1075 | 115 / 147 / 195 |
| annotation | 339 / 467 / 611 | 99 / 131 / 179 |
| form ↔ pattern interleaved (17 levels, 8 patterns) | 211 | 51 |
| `diagnose_redaction` walker, forms | 707 / 1027 / 1363 | 99 / 147 / 195 |

Per level: ≈ 25 KiB in debug, ≈ 5 KiB in release on the costliest path
(a soft mask's group).

**Decision: `max_xobject_depth` 32 → 48.** At 48 every path needs less
stack than v0.5.0 needed at 32. The worst case (a 48-level soft-mask
chain plus 8 pattern levels) is ≈ 1.3 MiB in debug — a 2 MiB thread
(std's default, and every test thread) keeps ≈ 0.7 MiB — and ≈ 0.25 MiB
in release, well inside wasm32's 1 MiB. 64 would leave ≈ 0.3 MiB in a
debug 2 MiB thread: too little. The one corpus document beyond 32
(`mlp-mixer`, 33–48 levels) renders all 48 pages.

The bound stays explicit (a caller can raise it with a larger stack, at
the per-level costs above) and is reported as
`LimitExceeded { limit: "max_xobject_depth" }`. Making the interpreter
iterative would remove the stack dependence altogether; it is a larger
change than this release and is not needed for the default.

Tests (`tests/render_xobject_depth.rs`): 47 and 48 levels render, 49 is
refused, on each of the five paths; a caller's limit applies both ways;
cycles stop; a refusal leaves the document rendering as before; every
path at the default depth in a 2 MiB (debug) / 512 KiB (release) thread,
run in a child process — checked to fail, without taking the runner
down, with a 256 KiB stack.

## 3. R4 — structured render fuzzing

Two new targets (`fuzz/README.md`):

- **`render_content`** (structured content stream): a fixed, valid page
  with every resource kind, its content stream generated from the input.
- **`render_graph`** (structured object graph): page trees and form
  graphs, broken references, object streams, rendered strict and in
  recovery mode.

`open_any`, `xref_updates`, `ciphertext` and `encrypt_dict` already
render arbitrary bytes (`exercise`); `text_sources` renders fonts; the new
targets add structure, so the interpreter's deep paths are reached
instead of the parser's refusals.

| structure | target | reached (`render.rs`, 5-minute corpus) |
|---|---|---|
| Catalog / Pages / Page, inheritance, shared page, `/Kids` cycle | `render_graph` | yes |
| indirect, shared, cyclic, undefined, other-generation references | `render_graph` | yes |
| object streams; deep dictionaries and arrays | `render_graph` | yes |
| `q`/`Q`, `cm`, `gs`, clip, blend modes, alpha, ExtGState | `render_content` | yes (`install_clip` 100 %, `apply_extgstate` partial) |
| Form XObject, nesting, cycles | both | yes (`do_form` 67 %) |
| image XObject (RGB, gray, 1-bit, soft-masked), inline images | `render_content` | yes (`paint_image` 100 %, inline 79 %) |
| transparency group, knockout | both | yes (`run_in_layer` 68 %, knockout 72 %) |
| soft mask (alpha, luminosity) | both | yes (65 %) |
| operand count errors, extreme / malformed numbers, undefined names | `render_content` | yes |
| shading (axial, radial), shading pattern | `render_content` | yes (`paint_shading_op` 82 %) |
| tiling pattern | both | yes (`paint_tiling` 77 %; the cached-tile path not yet) |
| text, standard font, Type 3 | `render_content` | yes (`show_text` 95 %, Type 3 82 %) |
| annotation appearance | `render_content` | yes (47 %) |
| TrueType / CFF / CID fonts, function-based and mesh shadings, images with filters, optional content | — | not in these targets (fonts: `text_sources`) |

Overall `render.rs` line coverage of a 5-minute `render_content` corpus:
59 %. The committed seeds alone reach 77 % (`render_content`) and 92 %
(`render_graph`) of that corpus's edges.

**Findings, both in every earlier release, fixed with failing tests
first** (`tests/render_extreme_widths.rs`):
1. A line width far beyond the page (`99999999999999999999 w`) with a
   stroked rectangle, join, cap or text panicked inside tiny-skia's edge
   builder. Now a stroke wider than 2^24 device px is narrowed to the
   width that covers the pixmap when that paints the same pixels, and
   refused (`Unsupported`, "stroke width") otherwise.
2. Geometry reaching ≈ 5 × 10⁸ device px (a triangle with a 10¹⁰ corner)
   panicked in tiny-skia's pipeline. Now a path beyond ±2^24 device px is
   skipped when it lies entirely off the pixmap (a clip there empties
   the clip) and refused (`Unsupported`, "geometry extent") otherwise.

**CI.** PR CI (`render-fuzz-smoke`) replays the seeds — the same inputs
every run — then runs 3000 new inputs from libFuzzer seed 1 per target
(≤ 180 s, 2 GiB, 10 s per input). Which inputs that phase reaches can
vary: coverage feedback follows the library's per-process hash order.
Each input's result is deterministic, and a failure uploads the input.
`fuzz-nightly.yml` (independent of the corpus nightly, no credentials)
fuzzes each target for 15 minutes daily, keeping the corpus in the
Actions cache. Cost ≈ 2 × 20 runner minutes a day.

## 5. Performance and memory

Release builds of v0.5.0 (`7125732`) and the branch, the same probe
(`render_page` on every page at 72 dpi, default limits, a 600 × 600 pt
page for the synthetic cases), three processes each; time per pass and
peak RSS (`/usr/bin/time -l`), macOS arm64:

| case | v0.5.0 | v0.5.1 dev |
|---|---|---|
| forms nested 32 | 1.9 ms, 17 MB | 1.9 ms, 16 MB |
| forms nested 48 | refused (`max_xobject_depth`) in 2.0 ms | **renders**, 3.1 ms, 22 MB |
| transparency groups nested 32 | 9.7 ms, 71 MB | 9.7 ms, 71 MB |
| transparency groups nested 48 | refused, 2.6 ms | **renders**, 14.9 ms, 105 MB |
| soft masks nested 32 | 3.6 ms, 61 MB | 3.6 ms, 61 MB |
| soft masks nested 48 | refused, 1.2 ms | **renders**, 5.7 ms, 89 MB |
| form cycle | `CycleDetected`, 0.14 ms, 5 MB | same |
| 200 000 fill operators | 286–334 ms, 224 MB | 265–273 ms, 224 MB |
| 5 000 small forms | 4.5–5.8 s, 17 MB | 4.4–4.9 s, 17 MB |
| `attention-is-all-you-need` (15 pages) | 2.37–2.61 s, 61–67 MB | 2.37–2.40 s, 61 MB |
| `arxiv-2204.06125` (27 pages) | 2.9–3.5 s, 301–349 MB | 2.9–3.4 s, 284–346 MB |
| `mlp-mixer` (48 pages, nested 33–48) | 47 pages + 1 refused, 3.6–4.2 s, 87–93 MB | 48 pages, 3.8–5.9 s, 96–100 MB |

For the same work the two are indistinguishable (the dispatch split
costs no measurable time). What 48 adds is the deeper documents
themselves, at the per-level cost of the shallower ones: a group level
holds a page-sized layer (here ≈ 2 MB at 72 dpi), already bounded
together with the page by `max_render_buffer_bytes`, so a 48-level
group chain at a high DPI is refused by that limit rather than growing
memory. Stack: § 2. The 5 000-forms case (≈ 1 ms per tiny form) is
the same in both and is not part of this work.

## 6. Graphics-state masks (found while measuring §5)

The clip (and, under a soft mask, the hard clip and the soft mask) is a
mask of one byte per page pixel. Every save — `q`, a form, a group, a
pattern cell — deep-copied it, outside any limit: `re W n` and 1000 `q`
cost 1000 masks, and each nested form one more. Every earlier release
has it; 48 instead of 32 levels scaled the form share by 1.5.

| case (600 pt page) | v0.5.0 | v0.5.1 dev |
|---|---|---|
| `re W n` + 1000 `q`, 600 dpi | 2221 MB, 2.86 s | 119 MB, 8 ms |
| 48 nested forms, one BBox, 72 dpi | refused (depth) | 5 MB |
| 32 nested forms, shrinking BBoxes, 600 dpi | 886 MB | `LimitExceeded` (800 MB of distinct masks) |
| `mlp-mixer` at 300 dpi | 47 pages + 1 refused (depth), 712 MB | 48 pages, 318 MB |
| `mlp-mixer` at 600 dpi | 47 + 1 refused (buffer) | 47 + 1 refused (buffer) |

Now: a saved state shares its masks (`Rc`); a clip changes an unshared
mask in place and a shared one in a copy, kept only when it differs; a
form or cell BBox whose device quad holds every pixel the clip lets
through is skipped (exact: a property test over random rectangles and
transforms checks that the intersection then changes no byte); and the
masks alive at once are bounded by `max_render_buffer_bytes`, as an
allowance of their own beside the page and its layers.

Counting masks *inside* the page-and-layers budget was measured and
rejected: `mlp-mixer` page 42 at 300 dpi holds 16 distinct, legitimately
different clip masks (135 MB) when it enters a group, and would have been
refused where v0.5.0 (with its depth limit raised) drew it.
