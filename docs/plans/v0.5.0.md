# Plan — v0.5.0: verified rewrites, measured robustness

Status: analysis and plan (2026-11-01), on v0.4.0 (`3b88768`), Linux
nightly 41277691417 (Poppler 26.01 with `poppler-data`) and a macOS
run of the same code. Per-file evidence lives in the gitignored
`compat/reports/v050/`; this file carries only aggregates, anonymised
causes and the plan.

## Method

| phase | how |
|---|---|
| Full PASS gap | every `expect: pass` document that is not a Full PASS (87 of 425) — each stage's first error, normalised, merged into one blocker set per document; every blocker classified (unsupported feature, bug, intentional limit / policy, malformed original, witness defect, gate false positive, environment, undetermined) |
| recoverability | a spike branch (not merged) with environment-gated bypasses of each rewrite refusal (the usage-rights bypass *removes* `/Perms`, i.e. option D1 (b)); the compat runner on the 87 documents with no bypass, each bypass alone and all together: which documents then reach a Full PASS and whether their round trip and semantic round trip pass |
| rendering | the runner's per-file approximations, quality classes and technology inventory (font kinds, image filters, shading, scripts); page-1 render time and peak RSS of the CLI on all 511 files |
| text | every `expect: pass` document with text whose page-1 multiset F1 is below 0.9 (37), split by where the missing characters are (page content, annotations, unresolved codes) |
| limits | the documents refused for a resource limit re-rendered with raised limits |

## 4. Decisions (design recorded 2026-11-01; implementation in phases B / C)

Both decisions concern safety and the public API; each is reviewed
independently again before its implementation starts.

### D1 — usage-rights signatures: refuse by default, remove on request

A usage-rights signature (`/Perms /UR`, `/UR3`) grants Reader features;
it does not certify or approve the content. A full rewrite cannot keep
it valid, and keeping it would make the output claim rights it no longer
has. Policy:

- **Default unchanged**: `rewrite` refuses a document with `/Perms /UR`
  or `/UR3` (`Error::SignaturePolicy`, `RewriteOfSignedDocument`), as
  in 0.4.0.
- **Opt-in removal**: only an explicit option removes the usage-rights
  signature; the output is an ordinary, unsigned form.
- **Never removed**: certification (`/Perms /DocMDP`), approval
  signatures (a signature field with `/V`), document timestamps, and any
  document whose usage-rights signature is also reachable as something
  else (below) stay refused with or without the option.
- **Not hidden**: the removal is returned as a structured record (what
  was removed, from where), never only as log text.
- **Verified**: the output must contain no reachable signature value —
  no signature dictionary (`/Type /Sig` or `/DocTimeStamp`, or any
  dictionary with `/ByteRange`) and so none of its `/Contents`, no
  `/Reference` with a `/TransformMethod` — and must pass the graph,
  render and semantic round trips with the removal declared.

`/Perms` is not the only path to a signature, so deleting the `/Perms`
entry alone is not proof of safety. Phase C must check, and refuse when
any is present: the same signature dictionary referenced from a field
(`/V`) or from another object; signature fields and `/Lock` /
`/SV` dictionaries; `/Reference` transform entries (`/DocMDP`,
`/FieldMDP`, `/UR3`); the catalog's `/DSS` (validation data) and
`/Legal`; `/AcroForm /SigFlags` (kept consistent with what remains —
bit 1 "signatures exist" must not claim a removed signature; the phase
C design clears it as part of the declared change, `rewrite-policy.md`
§5.2); and
signature content inside XFA packets (XML signatures in `datasets` /
`template`), which a byte-for-byte carry of the packet would keep. The
earlier revisions of an incrementally updated file are not carried by a
full rewrite and need no separate treatment.

API: the 0.4.0 signatures (`rewrite`, `rewrite_with_limits`) keep their
behaviour. The option and the record need an additive entry point — e.g.
`rewrite_with_options(&Document, &RewriteOptions) -> Result<Rewritten,
Error>` with a `#[non_exhaustive]` options builder and a result carrying
the bytes and the removals — checked with `cargo semver-checks` as a
minor-compatible addition. The name and shape are decided in phase C,
not here.

### D2 — executable content: carry, never execute, always report

kasane-pdf never executes JavaScript, and its default rewrite is not a
sanitiser (README). Policy:

- `rewrite` carries executable content verbatim: catalog `/OpenAction`
  (JavaScript included), catalog `/AA`, page / annotation / field `/AA`,
  annotation `/A`, and the `/Names /JavaScript` tree — replacing today's
  refusal of the catalog-level entries, which made the policy
  inconsistent (page-level scripts were already carried).
- Every carried script is **reported** to the caller (what kind, where),
  so none is retained silently; the API documentation states that
  another viewer may run them.
- The semantic round trip (`doc_actions`, `javascript`, phase A) must
  pass on every rewrite that carries them.
- Removing or neutralising scripts is a separate, explicit operation
  (like `remove_document_metadata`), considered after 0.5.0; it is never
  the default rewrite.

The report shares the structured result of D1 (one additive API for
both). The behaviour change (documents refused in 0.4.0 now rewritten)
goes into the CHANGELOG.

boundary cases then reproduced, with synthetic files, 6 of 7 signed

- UTF-16 without a byte order mark after white space;
- a non-ASCII namespace prefix;
- the namespace spelt with character references;
- a packet or `/Perms` behind a compressed object whose value is a

- DTD entities building the markup;
- UTF-7, EBCDIC, UTF-32 without a byte order mark, unexplained NUL

only in the XML-DSig namespace, and a namespace can only be bound by
writing its URI. The check:
1. reads each packet as ASCII-compatible text (UTF-16 detected and

2. expands numeric character references (any length);
3. refuses with `SignaturePolicy` when it finds `xmldsig` (any case,
   comments and CDATA included — conservative).

It does this per packet and then on all packets together, as the one
document they form. It refuses with `Unsupported` what it cannot read
completely: external data, encodings that are not ASCII-compatible or
contradict their declaration, any DTD. Every refusal check now follows
references through object streams too (64 hops, then a cycle error).

only has to answer "is the namespace written anywhere", which the
lexical scan answers completely once encodings, character references
and DTDs are handled. A parser would add a second reading of the XML
that could disagree with the reader that verifies the signature.

## 16. Final audit before integrating W2 (2026-11-02)

**The PDF 2.0 trailer `/ID`** (ISO 32000-2 §14.4, Table 15). It is
required in 2.0 and written for 2.0 output only (1.x output unchanged).
- The first element is permanent: the input's, kept across a rewrite,
  which is a modification of the same document.
- The second element changes with the content: the MD5 of the written
  file up to the cross-reference table (header, binary comment, every
  object). That excludes the xref table and the trailer, so the `/ID`
  is not part of what it hashes.

Tests:
- what is hashed;
- the identifier with and without an input `/ID`, and with a malformed
  one (then both elements are the digest: §14.4's "first written");
- content changed: the second element changes, the first stays;
- the same input twice: the same bytes;
- the output rewritten again, twice: the same file;
- 2.0 documents with page metadata and associated files;
- 1.x output: no `/ID`.

Encrypted documents are refused before the identifier is computed (it
takes part in their key derivation). No defect found in W2.

One finding outside W2, from before 0.5 and on every version: the
incremental writer copies the previous `/ID` unchanged, so the changing
identifier does not change on an incremental update. §14.4 says it
should. Recorded for the incremental writer (R phase); fixing it
changes every incremental output that has an `/ID`.

**`/OBJR`.** An XObject named only by a structure element's object
reference is an `/AF` owner the snapshot did not visit. It is now
visited (a small change; deduplicated through the same first-owner map,
cycle-safe through the form stack), with a test. Still not covered, and
therefore not claimed as preserved: `/AF` reached only through
- the resources of a pattern, a Type 3 font, a soft mask or the
  AcroForm `/DR`;
- a widget that is in no page's `/Annots`;
- pages that are not indirect objects.

**The two `version` fails.** Two inputs declare 1.4 but carry
`/OCProperties`, a 1.5 feature. The rewriter raises the header to 1.5
(since 0.4), so the output declares the version its content needs (ISO
32000-1 §7.5.2): the change is required, not an error. The category
separates the declared form (only noted) from the effective version (a
difference), and the effective version did change. So the category
reports it, and the comparison rule is not relaxed to hide it.

Proposal for the semantic round trip before any report-only category
is enforced: separate **detecting** a difference from **accepting** a
transformation.
1. The snapshot comparison stays as it is: it finds every difference.
2. A transformation table names the changes a writer may make, each
   with its condition, and the runner classifies a matching difference
   as `transformed` instead of `fail`. First entry: the effective
   version raised to the minimum its carried features require, never
   lowered, and the header only.
3. `transformed` is reported, never counted as `pass`. The baseline
   records it per file, and a new `transformed` is listed for review
   like a lost pass.

Conditions to promote a category to Enforced:
- every rule in its table has synthetic tests (applies, does not apply,
  and the near miss that must still fail);
- the category is `error`/`unsupported` on no corpus file;
- consecutive Linux nightlies show no unexplained `fail`;
- an independent review of the table.

**Independence of the new categories.** They are taken with their own
context and node budget after the others, and stored apart
(`report_only`). They are absent from `class`, from `checks` and from

## 18. Phase C design: rewrite policies (D2, D1) (2026-11-03, branch `design/v050-rewrite-policy`)

Design only. The detailed design is `plans/rewrite-policy.md`, the
decision record `decisions/rewrite-policy.md`.

**API.** `rewrite_with(&Document, &RewriteOptions) ->
Result<RewriteOutput, Error>`:
- `#[non_exhaustive]` options with builders, in the style of `Limits`;
- `ExecutableContentPolicy` (`Profile` (default) /
  `RefuseScriptsAndExternal` / `Carry`), `MultimediaPolicy` (`Refuse`),
  `UsageRightsPolicy` (`Refuse` (default) / `Remove`);
- a `#[must_use]` output owning the bytes and a content-free report.

With default options the bytes are exactly `rewrite`'s. The change is
additive (semver minor), with no feature flag.

**Audit of today's rewrite.** Only the document-level script entry
points are refused. Page, annotation, field and outline actions,
scripts reached through `/Next`, external actions and page-level
multimedia annotations are carried, without a report. Signature-like
dictionaries outside `/FT /Sig` fields, `/DSS` and `/Legal` are not
checked. D2 reports what the default carries without changing it. D1's
signature walker closes the gap for `Remove`. Whether `rewrite` and
`Profile` should refuse such dictionaries too is open decision 7 of the
design: it would change the default's results, so it is decided after
C2, with the walker's corpus effect measured.
